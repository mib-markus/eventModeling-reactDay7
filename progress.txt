## 2026-09-18 - CreateShift

- Started iteration: context is "shiftmanagement" (Shift Management), only Planned slice is CreateShift (STATE_CHANGE).
- No `.build-kit/.eventmodelers/config.json` present -> skipping board status sync (MCP/update-slice-status), working locally only.
- Created branch feature/createshift from day8.
- Set slice status to InProgress in index.json and slice.json.
- No screen HTML node available (no eventmodelers board MCP/token configured in this project's
  .eventmodelers/config.json — it only has agentIds, no token/board/org). Built the form from
  slice.json fields alone, following the existing BlockTable.tsx Bulma pattern (columns/field/control).
- Screen "Create shift" lane is "Manager" (from slice.json screens[].lane) -> path
  src/slices/shiftmanagement/manager/createshift/CreateShift.tsx. No other slice in
  .build-kit/.slices/*/index.json shares this screen title, so no src/pages/ composition needed;
  wired directly into App.tsx like the day7 slices.
- Business rules implemented client-side per specifications[]: recurring shift requires
  fromDay+toDay (recurrence_days_missing), endDateTime must be after startDateTime
  (end_before_start) - both block the submit button and show an inline warning. The
  "shift_already_created" duplicate-id spec is a server-side invariant (this stack has no DB) -
  surfaced generically via the existing ApiError/onError path used elsewhere in this codebase,
  same as BlockTable's error handling.
- shiftId defaults to crypto.randomUUID() when not passed as a prop (mirrors idAttribute:true
  field with no dedicated screen input - it's an internal id, not user-entered per the screen).
- Added samples/sample-1.json (recurring, from spec 1) and samples/sample-2.json (one-time, no
  fromDay/toDay, from spec 2), wired sample-1 into App.tsx.
- Verified visually via Playwright against `npm run dev` (VITE_DATA_MODE=mock): form renders with
  sample-1 data, unchecking "Recurring shift" correctly hides From day/To day fields, submit
  resolves via mock postCommand with no console errors.
- npm run build and npm run lint both pass clean.
- Committed as "feat: [CreateShift]" and fast-forward merged into main.
- Set slice status to Done in index.json and slice.json (board sync skipped, no config).
- **Learnings for future iterations:**
  - This project currently has no `.eventmodelers` board token/org configured (only
    `.eventmodelers/config.json` with `agentIds.BUILD`, no `token`/`boardId`/`organizationId`) -
    every board-dependent step (screen HTML fetch, update-slice-status, comments) has nothing to
    connect to. Treat this as expected per CLAUDE.md's "skip platform communication" rule rather
    than trying to run the `connect` skill's interactive setup mid-iteration.
  - Screen lane -> folder segment: `slice.json.screens[].lane` gives the lane directly without
    needing a board fetch when the board isn't reachable; use it as `laneSlug` (lowercased,
    hyphenated) same as the skill's Step 2 describes.
  - datetime-local `<input>` is the natural fit for `DateTime` typed fields with `YYYY-MM-DDTHH:mm`
    examples (matches slice.json's example format exactly, e.g. "2026-04-15T06:00").

## 2026-09-18 - ClockIn

- Started iteration: context "timetracking" (Time Tracking); highest-priority Planned slice was
  ClockIn (STATE_CHANGE, index 1). MyShifts (index 0) already Done; ClockOut/AttendanceHistory
  still "Created" — correctly left untouched.
- No `.build-kit/.eventmodelers/config.json` and `.eventmodelers/config.json` still has only
  `agentIds.BUILD` (no token/boardId/organizationId) -> skipped all board sync
  (update-slice-status/comments/screen fetch), same as CreateShift/MyShifts iterations.
- Branched `feature/clockin` from `main` (not `day9` — `day9` predates the MyShifts merge, so
  branching from `main` picks up the latest slice code instead of missing it).
- Set slice status to InProgress in index.json and slice.json.
- Screen "My shifts" is shared with MyShifts (Done) and ClockOut (still Created, not yet built) —
  per build-state-change Step 6 that would normally mean composing at src/pages/My shifts.tsx, but
  with no board token the real screen markup/marks still can't be fetched. Consistent with the
  documented precedent, built ClockIn.tsx standalone from slice.json fields alone and wired it
  directly into App.tsx.
- Built src/slices/timetracking/employee/clockin/ClockIn.tsx (lane "Employee" from
  slice.json screens[].lane). Props are exactly command.fields[]: employeeId, shiftId,
  clockedInAt (optional override, defaults to now), location (optional), terminal (optional).
  POSTs to `/api/day9/clockin/:employeeId` (apiEndpoint verbatim, employeeId interpolated into the
  path like CreateShift's `:shiftId`).
- The four rejection specifications (shift_not_active x2, not_assigned_to_shift,
  already_clocked_in) all depend on state ClockIn's command fields don't carry (shift timing,
  assignment, existing open ClockedIn) — the component has no way to validate them client-side
  without fetching data itself, which slice components must never do. Left these as backend
  invariants surfaced generically through the existing ApiError/onError path, same treatment
  CreateShift gave its server-side "shift_already_created" duplicate check.
- Added samples/sample-1.json (location+terminal, from spec 1) and samples/sample-2.json (no
  location/terminal, from spec 2 — "without location or terminal is allowed"). Wired sample-1 into
  App.tsx.
- Verified visually via Playwright against `npm run dev` (VITE_DATA_MODE=mock): form renders with
  sample-1's location/terminal pre-filled, clicking "Clock in" resolves via mock postCommand with
  no error notification.
- npm run build and npm run lint both pass clean.
- Committed as "feat: [ClockIn]" and fast-forward merged into main.
- Set slice status to Done in index.json and slice.json (board sync skipped, no config).
- **Learnings for future iterations:**
  - When branching for a new slice, prefer branching from `main`, not an older per-day branch like
    `day9` — day branches can predate later merges (day9 was missing the MyShifts commit already on
    main), so branching from an old day branch risks losing sibling slices' code.
  - A command's rejection specifications aren't automatically client-side validation candidates —
    only implement inline validation when the needed data is actually among the command's own
    fields (e.g. CreateShift's recurring/fromDay/toDay). When a rejection depends on server-side
    state the component was never given (shift timing, assignment, existing sessions), it's a
    backend invariant: let it surface through the standard ApiError/onError path instead of
    inventing a client-side check that would require the component to fetch data itself.
